# ADR-001: Keep the opt-in directory as a simple static interface with a worker-backed API when needed

Status: Accepted  
Date: 2026-11-03

## Context
The project continues the HW5 problem: interns want to learn about another team without signaling a desire to leave, while employees can opt in to a short informational conversation. The product must keep the interaction low-friction, fictional, and easy to inspect. The codebase is a static page plus an optional worker API, and the project constraints call for a small, explainable architecture that does not require a paid service or an external vendor-owned directory.

## The Gate
Build: Keep the interface in plain HTML, CSS, and JavaScript and use a small worker to persist entries and handle validation. This keeps the logic inspectable and aligned with the course requirement to understand every line of the app.
Buy: Use a hosted backend or directory service. This would reduce custom code, but it would add vendor-specific trust and deployment complexity with no real gain for a small prototype.
Delegate: Ask an AI builder or external platform to generate and host the app. This would be fast, but it would reduce the student’s ability to inspect the implementation and would weaken the course requirement for personal verification.

## Options considered
| Option | For | Against |
|---|---|---|
| Build | Lowest cost, inspectable, easy to explain, keeps the project in GitHub Pages or a tiny worker API | Requires custom validation and deployment setup |
| Buy | Less custom coding | Adds vendor cost and less inspectable trust boundary |
| Delegate | Fast delivery | Harder to audit and less aligned with the project’s learning goals |

## Decision
Build the directory as a simple static front end and keep the data and validation logic in a small worker-backed API only when needed. The page remains easy to understand, the data stays fictional and non-sensitive, and the architecture is still small enough to reason about by hand.

## Consequences
The project stays inspectable and low-cost, but the page depends on a small service boundary when a backend is used and some deployment work is required. A later change in project scope or a real multi-user requirement would trigger a revisit and could justify a different architecture.

Reversal trigger: if the problem requires separate user identities, real authorization, or production-grade moderation, this architecture should be superseded by a different ADR.
