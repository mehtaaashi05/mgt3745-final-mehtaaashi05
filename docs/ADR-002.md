# ADR-002: Use a static curated directory

**Status:** Accepted

**Date:** 2026-11-11

**Supersedes:** [ADR-001](ADR-001.md) and the historical Worker/D1 plan in
[context/ARCHITECTURE.md](../context/ARCHITECTURE.md)

## Context

The directory has two sides: employees opt in and interns search for someone
to contact. Browser `localStorage` is private to one browser and cannot share an
employee's opt-in with an intern on another device. The existing Worker was an
in-memory scaffold with no D1 binding or deployment, so it did not provide
shared persistence either. The professor confirmed that deployment may be a
static site if the architecture and product limitations are documented
accurately.

## Decision

Use a static site that loads curated profiles from `data/directory.json`.
Interns can search by profile name, team, or topic. The opt-in form creates a
copyable JSON snippet locally; it does not submit or publish the request. A
maintainer must review and manually curate any approved profile in the JSON
file. The current example profiles remain fictional.

No approved private intake or removal channel is configured. Do not enter real
employee details or publish them until explicit consent, organizational
approval, and an appropriate private intake and removal process are in place.

## Trust boundary

The directory JSON is public in both the repository and the deployed static
site. It contains profile names or aliases, teams, topics, and contact values.
Anyone who can reach the site can read it; repository write access controls who
can change the source data. The prototype has no authentication, server-side
storage, or analytics. The request form fields stay in the browser and are not
sent to the hosting provider by the application.

Before any real profile is published, an approved private channel must support
employee opt-in and opt-out. A removal request would be handled by the
maintainer changing the curated JSON and redeploying. This is not immediate or
self-service.

## Alternatives considered

- **Worker + D1:** could support shared updates, but the repository had no
  durable database binding or deployed API. It would require implementation,
  testing, and additional documentation for access and opt-out.
- **Browser `localStorage`:** rejected because it cannot share entries across
  employees' and interns' devices.
- **Static curated JSON:** selected because it can be hosted without an
  application server and supports an intern search flow. It requires manual
  curation and does not provide real matching until an approved opt-in process
  exists.

## Consequences

The directory source is portable and can be deployed as a static site. The
prototype can test search usability with fictional entries, but not whether
interns can contact actual opted-in employees. Real employee data remains out
of scope until a private intake and removal process is approved.

## Revisit trigger

Revisit this decision when a safe private opt-in and opt-out process is
approved, when live shared updates are needed, or when authenticated access is
required. A backend would need durable storage, documented read/write access,
retention, and opt-out behavior before real data is used.
