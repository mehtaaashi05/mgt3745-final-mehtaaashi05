# DDR-005: Align the HW7 audit and project records with shipped behavior

## Context

The professor's feedback and HW7 rubric require the documentation to describe
the actual architecture and its limits. Pages is enabled per the repository
owner's report, but the only recorded deployment failed before Pages was
enabled. No approved private opt-in or opt-out channel and no real-user search
test exist.

## Decision

Keep the static curated-JSON architecture. Clarify that the request form is a
local demo only, real employee details must not be used, and the fictional
directory does not provide real matching. Reconcile the original ADR, feature
criteria, deployment notes, sourcing audit, and tool ledger without claiming a
successful deployment or user test.

- `node --check app.js`: passed.
- JSON parsing for `data/directory.json` and `.devcontainer/devcontainer.json`: passed.
- Ruby YAML parsing for `.github/workflows/pages.yml`: passed.
- `git diff --check`: passed.

The GitHub Actions API currently reports only run
[43116196106](https://github.com/mehtaaashi05/mgt3745-final-mehtaaashi05/actions/runs/43116196106),
which failed because Pages had not been enabled. A successful deployment and
real-user search test remain external follow-up work.

## Consequences

The documents no longer imply that the app accepts opt-ins, supports private
opt-outs, or connects interns with real employees. The static search can be
evaluated with fictional sample profiles, but the product's real matching job
remains unvalidated until a safe intake and publishing process is approved.
